## Why the desktop stays empty

Two things are going on, and only one of them is about wallpapers.

First, Desktop Mode itself is still a developer feature. You turn it on in Developer options — it isn't something a normal user has switched on, and Android doesn't present it as finished.

Second, and this is the actual blocker: when a device is running the desktop experience, Android permits exactly one live wallpaper on a connected display, and it isn't yours. From [`WallpaperManagerService`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/services/core/java/com/android/server/wallpaper/WallpaperManagerService.java) at the `android-17.0.0_r1` tag:

```java
if (connection.mInfo != null) {                      // a live wallpaper
    if (isWallpaperDesktopExperienceEnabled
            && !isLiveWallpaperSupportedInDesktopExperience) {
        // Only allow the fallback wallpaper.
        return mFallbackWallpaperComponent != null
                && mFallbackWallpaperComponent.equals(connection.mInfo.getComponent());
    }
    return connection.mInfo.supportsMultipleDisplays();
}
```

`isLiveWallpaperSupportedInDesktopExperience` comes from a system resource in [`config.xml`](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/res/res/values/config.xml):

```xml
<!-- True if live wallpapers can be supported in the deskop experience -->
<bool name="config_isLiveWallpaperSupportedInDesktopExperience">false</bool>
```

It ships as `false`. So the early return fires and only the platform's own fallback component is allowed through. Note where that return sits: it happens *before* `supportsMultipleDisplays()` is consulted, so nothing an app declares about multi-display support is ever read.

This isn't new in Android 17, either. Diffing the AOSP tags, the check first appears in Android 16 r3 — so any Android 16 r3+ device driving a connected display behaves the same way.

## So why is it grey?

Because you are looking at a wallpaper. It just isn't yours.

"Only allow the fallback wallpaper" means the platform substitutes its own. On a Pixel 8 running Android 17, driving an external monitor over USB-C, both are on screen at once:

```
System wallpaper state:
  mInfo.component=app.wallpaperreactor/...WallpaperReactorLiveWallpaperService
   mDisplayId=0            <- ours, phone only
Fallback wallpaper state:
  mInfo.component=com.android.systemui/...GradientColorWallpaper
   mDisplayId=111          <- the external display
```

The flat `#A0A0A0` behind those windows is SystemUI's `GradientColorWallpaper`, doing exactly the job it was picked for.

## It isn't the app

Wallpaper Reactor already handles this case. The Android engine checks whether it's running off the primary screen and keeps rendering when it is:

```kotlin
fun isSecondaryDisplay(): Boolean =
    getCompatDisplayContext().display.displayId != Display.DEFAULT_DISPLAY
```

Every visibility decision in the wallpaper service takes that into account, so the engine stays alive on a display the phone isn't looking at. It never gets the chance here: `onCreateEngine` only ever fires for display 0, because the platform ruled our component out before asking.

## When it flips, this works

The interesting part is that this is a *config resource*, not a constant. An OEM can enable it with a resource overlay, so behaviour may already differ between manufacturers — Samsung DeX is worth trying on its own rather than assuming it matches a Pixel. There's a debug system property too, `persist.wm.debug.desktop_support_live_wallpaper`, which the same code reads before falling back to the resource.

And the change that introduced all this is titled "Add a config to enable live wallpaper in desktop experience." That's an opt-in switch shipped alongside a new capability, not a ban on something that used to work — live wallpapers were never drawn on connected displays before it existed.

So the day that resource flips to `true`, Wallpaper Reactor needs no new release. The secondary-display path is already written and tested; it's waiting on one boolean.

In the meantime live wallpapers work exactly as you'd expect on your phone's own screen, and if you plug into a desktop, the same library is waiting for you on Windows and macOS.
